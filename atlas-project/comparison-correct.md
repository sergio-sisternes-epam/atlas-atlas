## Content

Evaluate Atlas against systems that share the **storage and contribution** problem, not against chat-memory APIs.

A neighbour wins or loses on this test: can a second team mount the knowledge at a branch, add a requirement or lesson on their branch, open a PR the first team can compile, and keep working if the enterprise search plane is down?

### Neighbour classes (use these)

1. **InnerSource for knowledge** — open contribution inside the company; trusted committers; discoverability. Atlas applies this to claims, not only to libraries.
2. **Docs-as-code** — Mintlify, Docusaurus, GitHub Pages. Git-native narrative. Weak typed graph and work hubs.
3. **Spec-driven development** — GitHub Spec Kit and kin. Strong per-feature specify/plan/tasks loop. Weak as a durable org graph across modernisation and operations.
4. **ADRs / RFCs** — same job as Atlas `decision` pages, usually without mesh or compile.
5. **Service catalogs** — Backstage and peers. Inventory of systems, not behavioural memory that can branch.
6. **Controlled requirements tools** — Jira, Azure DevOps Boards, Jama, DOORS. Lifecycle yes; agent authorship and branch-fork of understanding no.
7. **Central wikis** — Confluence, ADO Wiki, SharePoint. Readable corpus; privileged write; fake branches.
8. **Enterprise retrieval** — Foundry IQ, Fabric IQ, Azure AI Search. Correct as *realization and read path* of merged Atlas claims plus other estate sources. Incorrect as the place knowledge is born.

### Pass/fail criterion

Knowledge that cannot travel with a branch is not team knowledge, however expensive the pool.

### Do not use as the primary set

Mem0, Zep/Graphiti, Letta, Cognee, LangMem, Supermemory. Those products answer “how does a chat agent remember a user fact?” Atlas answers “how does a team grow reviewed understanding beside the work?” The discarded frame is preserved under `wrong-path-agent-memory-layer/` so the mistake stays cheap to recognise.
